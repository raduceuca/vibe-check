# Audit findings: core

I read every file in packages/core/src and checked each suspected bug with throwaway tests: 17 vitest files in /private/tmp/claude-501/-Users-raduceuca-development-vibe-check/2abcf234-8de5-4ef0-ae23-4574b4eed6a1/scratchpad/audit/core/r2/ (run from packages/core with `npx vitest run --config <r2>/vitest.config.mjs --silent=false --reporter=verbose`), plus Playwright scripts that run the built packages/core/dist/index.js in installed Chrome against a mock hub with the real hub's CORS headers (`node <scratch>/audit/core/browser/<script>.mjs`). All of these ran this session, and every finding below cites its own output. The basics hold up: no `any`, no runtime imports in dist, import is SSR-safe, and the engine starts and stops in LIFO order. But the core loop is badly broken in three ways. (1) Reloading the page with nothing fixed records a "verified fix", because slow detectors have not run yet and cached assets report transferSize 0. A fix applied by hot reload (HMR) never verifies, because detector issues stay latched until a full page reload. (2) Several detectors add issues without limit. Within about 6 s the snapshot passes Chrome's 64 KB keepalive limit, the beacon stops, and the widget says "AI hub offline". (3) With the default config, every page gets two "Duplicate GET request" issues caused by VibeCheck's own SEO/AEO probes. The rest are real false positives or false negatives in memory-leak, INP, frame-rate, duplicate-requests, layout-thrashing, resource classification, heavy-library, image checks and SPA audits, plus overhead problems the tool itself causes (console-spam cost grows quadratically, and beacon traffic fills the 250-entry Resource Timing buffer in 160 s).

## C1 [blocker] Reloading with nothing fixed records a 'verified fix' (slow detectors and cached assets)
- file: packages/core/src/beacon/beaconClient.ts:78
- detail: The beacon posts a snapshot right at start() (line 78) and then every 2 s. The hub marks an issue 'fixed' after 2 snapshots without it (packages/mcp/src/workflow.ts:131-140). On a fresh page load, several detectors cannot have reported yet: heavy-library waits 3 s (heavyLibrary.ts:361/414), console-spam first checks at 10 s (consoleSpam.ts:133), memory-leak needs 4 samples at 5 s spacing, so 15 s or more (memoryLeak.ts:56), and layout-thrashing/long-task-attribution use buffered:false (so shifts and long frames from before engine start are never seen) and must see new events. seo/aeo/web-essentials only run 500/600 ms after window load (missing from the t=0 snapshot; missing from both snapshots if load takes longer than about 1.5 s). The snapshot has no way to say 'not evaluated yet', so absent is read as fixed. A second path: large-images (largeImages.ts:43) and resource-bloat (resourceBloat.ts:73) use transferSize, which is 0 on an HTTP-cache hit, so these issues vanish on reload even though nothing changed. The impact ledger counts every 'fixed' event as a verified fix.
- evidence: r2/verify.r2.test.ts (real VibeCheckEngine + mcp workflow, window.gsap present, no code change, reload): 'phases after reload (t=0s, 2s, 3.2s): verifying -> fixed -> regressed | impact: {"verifiedFixes":1,"regressionsCaught":1}'. Real Chrome browser/r2-cache.mjs: first load 'resource-bloat':['big-dep.js?v=abc123'],'large-images':['Large image: 600KB']; after reload both [] with 'hero.svg transfer=0 encoded=614514','big-dep.js?v=abc123 transfer=0 encoded=614404'.
- suggested fix: Add per-detector readiness to the snapshot (e.g. snapshot.evaluated: DetectorName[], or a warm-up flag per detector). The hub should only count a miss from a detector that has finished at least one full evaluation since start. For transfer sizes, use encodedBodySize (non-zero on cache hits) instead of transferSize. Add e2e coverage for a detector other than dom-bloat.
- verifier (confirmed): I re-ran r2/verify.r2.test.ts and got 'verifying -> fixed -> regressed | impact: {"verifiedFixes":1,"regressionsCaught":1}'. The code supports it. beaconClient.ts:78 sends at start() and the default interval is 2000 ms (types.ts:133). workflow.ts:131-140 moves an issue to 'fixed' after 2 absent snapshots and checks only snapshot.timestamp > requestedAt, with no instance or warm-up check. heavyLibrary.ts:361/414 does not scan until 3 s. consoleSpam.ts:133 first checks at 10 s. memoryLeak.ts:56 needs 4 samples at 5 s spacing. largeImages.ts:43 skips entries with transferSize 0, and resourceBloat.ts:73 uses transferSize, so cache hits on reload drop those issues and they are recorded as permanently fixed. hubStore.ts:131-145 writes impact receipts for each newly fixed issue. The verify step is the product's core promise, so this is a broken core loop.

## C2 [blocker] Unbounded issue growth exceeds the 64 KB keepalive limit; beacon dies and the widget says 'AI hub offline'
- file: packages/core/src/detectors/layoutThrashing.ts:56
- detail: layout-thrashing appends a new issue on every cluster of 3 shifts (line 56). console-spam appends a new issue per method every 10 s while spam continues (consoleSpam.ts:101-117). memory-leak re-appends whenever growth dips below 10% and climbs again (memoryLeak.ts:73-93). None of them deduplicate or cap. engine.getSnapshot() puts every issue into every beacon POST, sent with keepalive:true (beaconClient.ts:171). Chrome rejects a keepalive body over 64 KiB with TypeError, so send() sets lastOk=false and getAgentDisplayState (react AgentConnectionStatus.tsx:29) shows 'offline' / 'Cannot reach … Start the local hub', even though the hub is running. Separately, the hub schema rejects any snapshot with more than 500 issues (mcp/src/schema.ts:17). A JS-animated accordion, which is common, reaches this within seconds.
- evidence: Real Chrome browser/shifts.mjs (height animated via rAF): 't=5s layoutThrashing:99 snapshotBytes:50820 lastOk:true snapshotPostsReceived:3', 't=15s layoutThrashing:295 snapshotBytes:139097 lastOk:false snapshotPostsReceived:4', 't=30s layoutThrashing:589 snapshotBytes:270811 snapshotPostsReceived:4' (the hub got no POSTs after about 6 s). browser/keepalive.mjs: "'66KB keepalive': 'REJECTED: TypeError: Failed to fetch', '66KB no-keepalive': 'ok 200'". r2/spam.r2.test.ts: 'after 20 min of 3 logs/s: 120 console-spam issues, 72.9 KB of issues in every snapshot'. r2/schema.r2.test.ts: '501 issues accepted: false'.
- suggested fix: Make the issue list keyed and bounded: one issue per stable identity, updated in place with count/lastSeen, plus a global cap (e.g. 100 issues, and 50 LoAF entries without scripts). Drop keepalive for routine snapshot POSTs (keep it only for pagehide), or cap the body under 60 KB. Report a payload-too-large or schema-rejected failure as its own status rather than 'hub offline'.
- verifier (confirmed): Confirmed in code. layoutThrashing.ts:56 appends one issue per 3-shift cluster with no cap or dedupe. consoleSpam.ts:101-117 appends one per method on every 10 s check. memoryLeak.ts:73-93 re-appends after lastReportedSeverity resets. engine.collectIssues (engine.ts:264-273) sends all of them in every POST, with keepalive:true (beaconClient.ts:171). The fetch spec caps keepalive bodies at 64 KiB, and the catch sets lastOk=false, which AgentConnectionStatus.tsx:29 maps to 'offline'. Re-running the reproductions gave 'after 20 min of 3 logs/s: 120 console-spam issues, 72.9 KB', 'after 60s of a ticker shifting every 100ms: 200 layout-thrashing issues, 87.6 KB' and '501 issues accepted: false' (schema.ts:17). The connection dies and the widget misreports it, under the very conditions the detectors are built to catch.

- detail: With the default config, the seo detector fetches /robots.txt (seo.ts:218), and the aeo detector fetches location.href twice (aeo.ts:143 and 152, the second with Accept: text/markdown) and /robots.txt again (aeo.ts:159), all within about 100 ms. These go through the duplicate-requests fetch patch, which only ignores the beaconUrl prefix (engine.ts:141-143), so two warnings appear on every page that the user's code cannot cause or fix. An agent sent one of them will hunt for a fetch that does not exist, and the issue comes back on every reload. On sites without these files the probes also log red 404 'Failed to load resource' errors in the console on every load (5 per load in shifts.mjs).

- suggested fix: Make the audit probes fetch with the unpatched original fetch (capture globalThis.fetch at module init, or pass a probe fetch into the detectors), or tag probe requests so duplicateRequests ignores them. Also fetch robots.txt once and share it between seo and aeo.

## C4 [major] A fix applied by hot reload (HMR) never verifies: detector issues stay latched until a full reload
- file: packages/core/src/detectors/duplicateRequests.ts:62
- detail: Every detector except dom-bloat only ever adds issues; it never removes one when the condition clears. duplicate-requests, console-spam, memory-leak, layout-thrashing, long-task, heavy-library, images, resource-bloat, seo, aeo and web-essentials all keep issues until clear() or engine restart, and the widget never calls clearIssues (no caller in packages/react/src). After an agent fix applied by Vite/Next hot reload, the snapshot still carries the stale issue, so the hub's recordPresentIssue sets 'verification-failed' and moves the issue back to 'working' (mcp/src/workflow.ts:111-121). The verify-loop e2e (e2e/mcp-roundtrip/mcp-roundtrip.spec.ts:325-372) only uses dom-bloat, the one detector that retracts its issue (domBloat.ts:82-83), so this gap is untested.
- evidence: r2/hmr.r2.test.ts: 'phase 10s after an HMR fix: working | events: detected,verification-requested,verification-failed'. r2/dup.r2.test.ts: 'duplicate-requests issues 10 minutes after the last request: 1'.
- suggested fix: Give stateful detectors a 'still occurring' window: drop or mark an issue inactive when its condition has not recurred for N seconds (duplicate request not repeated in 30 s, no spam in the last window, heap recovered, and so on), and re-run the one-shot audits on demand or on a timer. Add a verify e2e for a latched detector such as duplicate-requests.
- verifier (confirmed): I re-ran hmr.r2 and got 'phase 10s after an HMR fix: working | events: detected,verification-requested,verification-failed'. dup.r2 shows the issue still present 10 minutes after the last request. Only domBloat.ts:82-83 clears its issues. clearIssues has no caller in packages/react/src, and core/react have no HMR hook. workflow.ts:111-121 turns a present issue into verification-failed. The e2e verify test (mcp-roundtrip.spec.ts:325+) exercises only dom-bloat.

## C6 [major] VibeCheck's own beacon/status traffic fills the 250-entry Resource Timing buffer in about 160 s, blinding the buffer-based detectors
- file: packages/core/src/beacon/beaconClient.ts:175
- detail: Each successful snapshot POST also triggers refreshStatus (line 175) on top of the separate 2 s status interval (line 76). An idle tab therefore makes 10 POSTs plus 20 status GETs every 20 s, and each one is a PerformanceResourceTiming entry. Once the default 250-entry buffer is full, performance.getEntriesByType/ByName stop returning new entries. resource-bloat (resourceBloat.ts:68), large-images (largeImages.ts:41) and heavy-library script matching (heavyLibrary.ts:313) read only that buffer, so anything loaded after about 3 minutes is never flagged. The host app's own buffer readers lose data too. Background tabs keep POSTing (5 POSTs in 10 s while hidden).
- evidence: Real Chrome browser/chatter.mjs: "hub requests from ONE idle tab in 20s: {'POST /api/snapshot': 10, 'GET /api/projects/:id/status': 20, 'OPTIONS /api/snapshot': 3}". browser/r2-beaconbuffer.mjs (page makes zero requests of its own): 'seconds until beacon traffic alone filled the 250-entry buffer: 160', composition {'/api/snapshot':81,'/api/projects/:id/status':161,...}. A 600 KB lazy chunk and a 600 KB image loaded afterwards: chunkInBuffer:0, imgInBuffer:0, resourceBloatIssues:[], largeImagesIssues:[] (the observer-based collector did see 'lazy-route-chunk.js 600KB','hero-big.svg 600KB').
- suggested fix: Have resource-bloat, large-images and heavy-library consume PerformanceObserver({type:'resource', buffered:true}) entries (the ResourceCollector already does) instead of getEntriesByType. Remove the extra refreshStatus after each send, skip sends while document.hidden, and consider sending only on change.
- verifier (confirmed): Code: beaconClient.ts:76 polls status every 2 s, :175 refreshes status again after every successful POST, and send() has no document.hidden gate. Nothing calls setResourceTimingBufferSize or clearResourceTimings in packages/. resourceBloat.ts:68, largeImages.ts:41 and heavyLibrary.ts:313 read only the buffer, not an observer. The real-Chrome output (r2-beaconbuffer.out) shows the buffer full at 160 s, with 81 snapshot and 161 status entries, then chunkInBuffer:0, imgInBuffer:0 and no resource-bloat or large-images issues, while the observer-based collector did see both 600 KB resources.

## C7 [major] Memory-leak heuristic fires 'error' on normal apps (boot-then-plateau, bounded sawtooth heap)
- file: packages/core/src/detectors/memoryLeak.ts:58
- detail: The baseline is the first sample taken at engine start, during app boot (line 58). The 'recovery' test only checks whether a second-half sample falls below baseline × 1.05 (lines 67-69). A heap that grows during boot and then stays flat never drops below the boot baseline, so it is reported as a leak after 15 s (only 4 samples are needed, line 56). A normal GC sawtooth also trips it repeatedly, because lastReportedSeverity resets whenever growth falls under 10% and a fresh issue is appended each time.
- evidence: Real Chrome browser/r2-memboot.mjs (8 s boot, then heap flat): heapMBEvery5s [9.2,16.7,16.7,16.7,16.7,16.7,15.4,15.2,15.2] -> 'error: Potential memory leak (1247% growth)'. browser/memleak.mjs (fixed-size ring buffer, no leak): heap [27,40,41,28,14,53,...] -> 2 issues 'error: Potential memory leak (2145% growth)', 'error: Potential memory leak (95% growth)'. r2/mem.r2.test.ts: flat 25 MB after boot -> ["error","Potential memory leak (25% growth)"].
- suggested fix: Ignore the first 30-60 s after start. Use a long window (2 min or more) and a trend on post-GC minima (the rolling minimum of each window, which must keep rising) rather than first-vs-last. Require monotonic growth of the minima across several windows. Keep one issue and update it instead of appending.
- verifier (confirmed): memoryLeak.ts:56-69: baseline = samples[0] of the 30 s window, 4 samples are enough, and 'recovery' only means some second-half sample is below baseline×1.05. A heap that grows during boot and then plateaus can never go back below the boot baseline, so it is reported as an 'error' leak at about 15 s. The real-Chrome output (r2-memboot.out) is a heap flat at 16.7 MB after boot reported as 'error: Potential memory leak (1247% growth) — Heap grew from 1.2MB to 16.7MB'. memleak.out shows 2 error issues for a bounded ring buffer. One small correction: the baseline slides with the window and is not only the engine-start sample, but during the first 30 s it is the boot sample, so the conclusion holds.

## C10 [major] Frame-rate 'dropped frame' threshold equals the frame budget: idle 60 Hz page reports about 60% dropped
- file: packages/core/src/collectors/frameRate.ts:61
- detail: A frame counts as dropped when duration > 16.67 ms (lines 7, 33, 61). rAF timestamps are coarsened (Chrome 100 µs, Firefox 1 ms) and vsync jitters, so a perfectly on-time 60 Hz frame measures 16.6 to 16.8 ms and a large share of them count as dropped. At 30 fps (iOS Low Power Mode) or on 50 Hz displays every frame is 'dropped' (smoothness 0%). droppedFrames and smoothness are public API (documented in apps/web/content/docs/concepts/collectors.mdx:61,75) and go to agents in get_performance_snapshot.
- evidence: Real Chrome browser/r2-fps.mjs, idle static page, headless 60 Hz: 'fps=60 dropped=38 smooth=36.7%', 'fps=61 dropped=36 smooth=41%' with raw rAF deltas [16.7,16.6,16.7,16.7,16.7,16.7,16.6,16.6,16.7,16.7,16.6,16.8]. On the 120 Hz headed display: 100%. r2/frame.r2.test.ts: 0.1 ms coarsening -> droppedFrames 39/59, smoothness 33.9; steady 30 fps -> smoothness 0.
- suggested fix: Estimate the display interval (median delta) and count a frame as dropped only when delta > 1.5× that interval (or round(delta/interval) − 1 missed vsyncs). Do not hard-code 60 Hz.
- verifier (confirmed): frameRate.ts:7/33/61 counts a frame as dropped when duration > 1000/60. I re-ran frame.r2 and got 0.1 ms resolution -> droppedFrames 39/59, smoothness 33.9, and steady 30 fps -> smoothness 0. The real-Chrome rAF deltas in the finding (16.6–16.8 ms) fall on both sides of the threshold. The main widget does not render smoothness or droppedFrames, but they are public and documented (collectors.mdx:61,75 shows '{smoothness}% smooth'; useFrameRate) and reach agents raw through get_performance_snapshot. Major stands, at the low end.

## C12 [minor] initiatorType 'css'/'link' treated as 'is CSS': background images and fonts reported as 'Large CSS resource'; fontTransferKB is always 0
- file: packages/core/src/detectors/resourceBloat.ts:37
- detail: initiatorType says who requested the resource, not what it is. 'css' means a url() from CSS (background images, @font-face, @import), and 'link' means any <link> (preload of fonts or images, icon, modulepreload). resourceBloat.ts:37/48 and resources.ts:18-24 classify both as CSS, and resources.ts:23 matches initiatorType 'font', which does not exist in the Resource Timing spec. - suggested fix: Classify by URL extension or response MIME type (PerformanceResourceTiming has no MIME type, so use the extension plus initiatorType as a hint): .woff/.woff2/.ttf/.otf -> font, image extensions -> image, .css -> css, .js/.mjs -> js. I lowered it to minor: no consumer of fontTransferKB or cssTransferKB exists in react/mcp/docs, the issue URL shows the real file type to the agent, and the impact is a mislabel plus generic advice, not a missed or false detection.

## C13 [major] heavy-library substring selectors misfire: 'assistant-message' becomes Ant Design (350KB); every Emotion app is reported as Material UI
- file: packages/core/src/detectors/heavyLibrary.ts:159
- detail: `[class*="ant-"]` (line 159) matches any class containing 'ant-': assistant-, variant-, important-, elegant-, tenant-, relevant- and so on. 'assistant-message' is ubiquitous in vibe-coded AI chat UIs.
