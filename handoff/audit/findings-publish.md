# Audit findings: publish

I packed all three public packages with `pnpm pack` into scratchpad/audit/publish/tarballs. The tarballs contain only dist, README, LICENSE and package.json: no tests, no `workspace:` specifiers, no runtime import of the private protocol package, and the sourcemaps carry their source content. `npx -y publint run <tgz> --strict` (v0.3.12 and v0.3.25) and `npx -y @arethetypeswrong/cli <tgz>` both came back clean for all three. The mcp bin has its shebang and executable mode. Running the packed mcp through `npx --package=<tgz>` resolved SDK 1.32.2 and zod 3.25.76, and an MCP stdio client then saw all 10 tools. The hook blocked `npm i` of named packages, so I built the consumer apps from the extracted tarballs plus symlinks into the repo's pnpm store (React 19.2.4 / Vite 8.0.1 / Next 16.2.10). React 18 was not available that way and is not runtime-tested [UNVERIFIED]. In the Vite consumer, every README usage typechecks under strict mode with skipLibCheck off, and `vite build` passes with the widget fully tree-shaken from production. But the component the `setup` CLI generates fails the stock `tsc -b` step. In the Next consumer, `next build` passes with the setup wrapper, fails when `<VibeCheck/>` is imported from a server component, and gives hydration errors in Chrome. Compared with npm 0.3.0, the workspace is still at 0.3.0. It adds the `up` CLI and new core exports (formatSetupPack, UP_START_COMMAND, SetupPackOptions), has no CHANGELOG entry, and `pnpm -r publish --dry-run` currently reports "There are no new packages that should be published". Recommended next version: 0.4.0 (minor). The changes are additive features: a new CLI subcommand, new public exports, changed `setup` output and a widget redesign. That matches the project's 0.2.0→0.3.0 minor cadence, and existing `^0.3.0` users are not moved silently onto a widget whose setup pack pins a different mcp version.

## P5 [major] Widget causes React hydration failures under SSR (Next.js), including from the setup-generated layout wrapper
- file: :
- detail: There are two separate render branches where server and client disagree. (a) `CANVAS_OK` is a module-level `typeof document !== 'undefined'` check. On the server it renders the SVG FpsTrace; on the client it renders Suspense plus the lazy Liveline. Any SSR page that renders the widget expanded therefore fails hydration on every load, even with empty storage. (b) `usePreferences` reads localStorage inside its useState initializer. Once a user expands the pill or changes theme, the server still renders the collapsed dark default while the client renders the stored state. With `<VibeCheckDevtools/>` mounted in app/layout.tsx as the README tells users to, that mismatch sits at the root body, so React regenerates the whole document and the Next dev overlay shows a hydration error on every reload. The marketing site avoids both problems only because it uses `dynamic(..., { ssr: false })` (apps/web/components/vibe/VibeWidget.tsx:10).
- evidence: packages/react/src/panels/monitor/FpsTrace.tsx:14 `export const CANVAS_OK = typeof document !== 'undefined' && ...`; packages/react/src/panels/monitor/MonitorView.tsx:170-191 branches on CANVAS_OK; packages/react/src/hooks/usePreferences.ts:14-16 `useState(() => readPreferences(...))`. Chrome against `next start` /client page (fresh storage) → `Minified React error #418`. Same page under `next dev` → `Hydration failed ... + <Suspense fallback=...> - <svg width="100%" height="24" viewBox="0 0 292 24"`. Under `next dev` on / with the setup wrapper in layout, after `localStorage['vibe-check:preferences:my-storefront']={collapsed:false,theme:'light'}`: `+ data-wcgw-theme="light" - data-wcgw-theme="dark" ... + data-testid="vibe-check-annotations" - data-testid="vibe-check-overlay"`. The / route without the widget showed no React errors.
- suggested fix: Make the first client render match the server. Detect canvas support in a useEffect or useSyncExternalStore (server snapshot false), and read preferences after mount (useEffect, or useSyncExternalStore with getServerSnapshot returning the defaults). A simpler option is a `mounted` gate in VibeCheck/PerfToggle that renders null until after the first effect; the widget is fixed-position, so there is no layout shift. Add an SSR hydration test with react-dom/server plus hydrateRoot.
- verifier (confirmed): The code confirms both server/client divergences. FpsTrace.tsx:14 sets CANVAS_OK at module level from `typeof document`, and MonitorView.tsx:170-191 renders the SVG FpsTrace on the server but Suspense+Liveline on the client. usePreferences.ts:14-16 reads localStorage in its useState initializer (readPreferences returns defaults when localStorage is undefined). The prior consumer's next-dev.log shows `Hydration failed` with the diff `+ <Suspense fallback=...> - <svg width="100%" height="24" viewBox="0 0 292 24"` on /client. A later entry shows the collapsed pill mismatching (`0 fps, 18 problems` vs `0 problems`) from cached issue state, so even the collapsed setup wrapper mismatches once issues are cached. The site docs recommend ssr:false, but they also list a plain 'use client' import as an option, and the setup CLI generates a non-dynamic wrapper. I did not re-run Chrome myself; the evidence is the code plus the existing logs.

## P6 [major] `setup`-generated VibeCheckDevtools.tsx fails `tsc -b` in a stock Vite react-ts app, breaking `npm run build`
- file: :
- detail: `renderDevtoolsComponent` emits `process.env.NODE_ENV`. The template's build script is `tsc -b && vite build`, so following the README Quick start breaks the user's production build. Runtime is fine, because Vite rewrites `process.env.NODE_ENV` to "development".
- evidence: packages/mcp/src/setup.ts:137 `if (process.env.NODE_ENV === 'production') return null`. Repro in scratchpad/audit/publish/consumer-vite with the packed CLI: `VIBE_CHECK_REGISTRY_PATH=... node node_modules/@wcgw/vibe-check-mcp/dist/index.js setup --agent cursor --project my-storefront` → creates src/VibeCheckDevtools.tsx. Copy demo/tsconfig{,.app,.node}.json, then `tsc -b` → `src/VibeCheckDevtools.tsx(6,7): error TS2591: Cannot find name 'process'. Do you need to install type definitions for node?`. All README usage examples in the same project typecheck clean.
- suggested fix: Choose the guard per framework in setup. If `vite` is a declared dependency, emit `if (!import.meta.env.DEV) return null`; for Next and others, keep `process.env.NODE_ENV`. Alternatively, emit a module-local `declare const process: { env: { NODE_ENV?: string } }` in the generated file. Add a setup test that type-checks the generated file against a vite/client-only tsconfig.
- verifier (confirmed): Reproduced independently. I used demo/tsconfig.app.json (types:['vite/client']) and the exact renderDevtoolsComponent output from setup.ts:133-146, with @types/node present. tsc gives `src/VibeCheckDevtools.tsx(6,7): error TS2591: Cannot find name 'process'`. demo/package.json shows the stock `"build": "tsc -b && vite build"`, so a stock Vite react-ts app that follows the setup quick start fails `npm run build`.
