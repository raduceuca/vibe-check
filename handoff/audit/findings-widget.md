# Audit findings: widget

I audited packages/react/src and its dist for a public release. The bundle passes its size budget: `node packages/react/scripts/size-check.mjs` reports 33.6 KB gzip against a 45 KB budget, and `npm pack --dry-run` gives a 234 KB tarball. The dist and src contain no print-proof strings. Two things block Next users. The dist has no 'use client' directive. And an SSR→hydrateRoot repro (scratchpad/audit/widget/ssr/hydrate.mjs and hydrate-issues.mjs) shows "Hydration failed" whenever stored prefs or persisted issues exist, which means every reload after the first session; that includes the component the setup CLI scaffolds. I ran the demo on :5391 and drove it with Playwright 1.61 at 390px and 1440px across these states: hub offline; waiting (an isolated real hub on :4291 proxied in, with HOME set to scratch); connected and conflict (mocked /status and /dispatch); light theme; and reduced motion. I looked at the screenshots, measured ghost pixels to rule out a bleed-through false alarm, and then stopped both servers. The repo was not modified. Confirmed defects: "mark as fixed" does nothing and throws an unhandled "Failed to fetch" when the hub is offline. The first "Copy" button in the onboarding card copies a Codex-only setup pack while the client picker is hidden, and it sits next to a second, identical-looking "Copy". The default Alt+Shift+V toggle compares event.key, which macOS changes to "◊". This follows from the code and is not reproduced on real hardware. The npm README still embeds the retired LIVE PROOF / CMYK / PL 0x screenshots. About 20 readable labels render at 11–13px. A transformed ancestor breaks the fixed panel because nothing is portaled. Other findings: missing button hover states, a flash of "hub is ready" while the hub is down, about 2 console errors per second with no backoff when offline, horizontal page overflow from the annotation layer, and accessible names that hide what a button does. All screenshots are in /private/tmp/claude-501/-Users-raduceuca-development-vibe-check/2abcf234-8de5-4ef0-ae23-4574b4eed6a1/scratchpad/audit/widget/.

## W1 [major] SSR hydration mismatch on every reload after first use (affects the setup-CLI scaffold in Next)
- file: packages/react/src/hooks/usePreferences.ts:14
- detail: Initial state is read from localStorage inside useState initializers. On the server these fall back to defaults; on the client they return stored values. Any persisted issue (always present after one session) or a stored collapsed/theme preference makes the first client render differ from the server HTML. React then throws away the server tree and Next's dev overlay shows a hydration error. The `setup` CLI scaffolds a plain 'use client' wrapper around PerfToggle with no ssr:false (packages/mcp/src/setup.ts:133-146), so the official setup path hits this. The project's own site avoids it only through dynamic(..., {ssr:false}) (apps/web/components/vibe/VibeWidget.tsx:11-14).
- evidence: packages/react/src/hooks/usePreferences.ts:14-16; packages/react/src/store/issueStore.ts:98 via packages/react/src/hooks/useIssueStore.ts:28; packages/react/src/hooks/useIssueWorkflow.ts:20-22; packages/react/src/hooks/useFpsHistory.ts:41. Repro: `node scratchpad/audit/widget/ssr/hydrate.mjs` renders the dist with renderToString(PerfToggle) and hydrates in jsdom with stored prefs → 'RECOVERABLE: Hydration failed because the server rendered HTML didn't match the client'. hydrate-issues.mjs, with only one persisted issue in 'vibe-check:issues:ssr-demo', gives the same error.
- suggested fix: Render a deterministic first pass. Seed state from the SSR-safe defaults, then read localStorage in a useEffect, or use useSyncExternalStore with a getServerSnapshot. A cheaper alternative: mount nothing until after hydration (a `mounted` flag), and make setup.ts emit a dynamic(ssr:false) wrapper for Next projects.
- verifier (confirmed): I re-ran scratchpad/audit/widget/ssr/hydrate.mjs and hydrate-issues.mjs against packages/react/dist. With a stored preference or a single persisted issue, both give 'RECOVERABLE: Hydration failed because the server rendered HTML didn't match the client'. My baseline copy with no localStorage writes (widget-verify/hydrate-baseline.mjs) gives 0 hydration errors, so the persisted state is the cause. The useState initializers that read storage are at usePreferences.ts:14-16, useIssueStore.ts:28 and useIssueWorkflow.ts:20-25. The setup scaffold (packages/mcp/src/setup.ts:133-146) is a plain 'use client' wrapper with no ssr:false. The site avoids the problem only through dynamic(...,{ssr:false}) (apps/web/components/vibe/VibeWidget.tsx:10-13).

## W3 [major] Default Alt+Shift+V toggle does not match on macOS (event.key is the Option-composed glyph)
- file: packages/react/src/PerfToggle.tsx:29
- detail: matchesShortcut compares event.key.toLowerCase() to 'v'. On macOS, Option changes the produced character, so Option+Shift+V reports event.key '◊' with event.code 'KeyV', and the documented default never matches on the platform most solo AI-frontend builders use. The unit tests pass because they dispatch a synthetic {key:'v', altKey:true}. The demo app mounts <VibeCheck> directly, so the shortcut is never exercised end to end. I did not reproduce this on a physical keyboard: Playwright synthesizes key events without the OS Option composition.
- evidence: packages/react/src/PerfToggle.tsx:25-29 (`event.key.toLowerCase() === parsed.key`), default `shortcut = 'alt+shift+v'` at :35. packages/react/src/__tests__/PerfToggle.test.tsx:58-60 uses key:'v' with altKey. README.md says 'press Alt+Shift+V to hide/show it'.
- suggested fix: Match single-letter and digit keys on event.code (`KeyV`/`Digit1`), falling back to event.key for named keys. Add a test that sends {key:'◊', code:'KeyV', altKey:true, shiftKey:true}.
- verifier (confirmed): PerfToggle.tsx:25-29 matches with `event.key.toLowerCase() === parsed.key`, and the default is 'alt+shift+v' (:35). On macOS, browsers report the Option-composed character in KeyboardEvent.key (Option+Shift+V gives '◊', code 'KeyV'), so this comparison can never be true there. Nothing in packages/react/src reads event.code (grep finds nothing), and the test uses a synthetic {key:'v', altKey:true} (PerfToggle.test.tsx:58-62). The shortcut is documented in packages/react/README.md:78, README.md:72 and skills/vibe-check/SKILL.md:30. Like the auditor, I could not test a physical keyboard; the macOS key composition is well-documented platform behaviour.
