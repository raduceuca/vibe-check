## E2E-02 [major] An undelivered dispatch is dropped when the agent releases, exits, or the hub restarts, and the issue stays 'Sent' with Send to agent disabled
- file: packages/mcp/src/hubStore.ts:281
- detail: The dispatch queue lives only in memory. releaseLease empties it (`queue: []`), and a hub restart loses it. The workflow phase 'sent' is persisted to .vibecheck/state.json and nothing ever reverts it. The bridge also calls release when stdin closes (index.ts:72 → leases.stop), so simply closing the agent session drops anything queued. In the widget, a phase of sent/working counts as `sent` and disables the button (IssueActions.tsx:121, `disabled={... || sent}`, title 'This issue was sent to the connected agent'). That leaves no way to resend: the loop breaks for that issue, and the UI says it was delivered. Combined with E2E-04, it takes only one Send click after the agent's watch has timed out.
- evidence: In mcp-honesty.mjs T2, the owner's watch timed out, then dispatch returned {ok:true,code:'dispatched',queueDepth:1} and the phase became 'sent'. Owner release_project gave status {state:'no-agent',queueDepth:0} with the phase still ['console-spam','sent']. Watcher B's watch_for_issue then got watch-timeout and the phase stayed 'sent'. In restart-queue.mjs, after dispatch (queueDepth 1) and a SIGTERM restart of the hub, the phase was still ['duplicate-requests','sent'], status was queueDepth 0, and the next watch_for_issue got watch-timeout.
- suggested fix: When a lease is released or expires, or when queued items are not restored on restart, append a 'send-dropped' event and move undelivered items back to 'detected'. Alternatively, persist the queue in state.json. Only treat an issue as 'sent' in the UI after a watcher has dequeued it, and allow resending whenever no delivery receipt exists.
- verifier (confirmed): I reproduced this on a live hub on port 4391. Dispatch returned {ok:true,code:'dispatched',queueDepth:1} and the phase became 'sent'. After release, status was {state:'no-agent',queueDepth:0} and the phase stayed 'sent'. A new owner B then got watch-timeout. In code, releaseLease (hubStore.ts:281) sets queue: [], persistence.ts saves only the workflow, nothing moves a phase back out of 'sent', and IssueActions.tsx:83/121 disables Send for sent/working. Downgraded from blocker for two reasons. The happy path works. A watch timeout alone does not lose anything: releaseExpiredLeases keeps the queue and the next watch_for_issue gets the item. The 'one Send click after a timeout' claim is overstated, because loss also needs a release, a bridge exit or a hub restart. 'Copy prompt' still works as a manual fallback.

## E2E-03 [major] A watch_for_issue that the agent client times out on or cancels still takes the next Send to agent, and that issue is lost as 'With agent'
- file: packages/mcp/src/mcpServer.ts:176
- detail: timeout_seconds accepts up to 300 (mcpServer.ts:171). The MCP SDK's default client request timeout is 60s (DEFAULT_REQUEST_TIMEOUT_MSEC = 60000 in SDK 1.27.1). When the client gives up or the user cancels, the SDK sends notifications/cancelled and discards the handler's result (protocol.js:365, `if (abortController.signal.aborted) return`). The tool handler ignores `extra.signal`, and hubClient.waitForIssue (hubClient.ts:175) issues fetch without an AbortSignal. So the hub-side long-poll waiter stays registered (hubServer.ts:406). The next widget dispatch is dequeued into that dead request: the phase becomes 'working' and the state 'busy' (widget shows 'With agent' / 'Agent working'), and the agent never sees it. Codex's per-tool timeout is also reportedly 60s by default [UNVERIFIED].
- evidence: In mcp-honesty.mjs T4, `watch_for_issue({timeout_seconds:90})` threw after 60002ms with code=-32001 'MCP error -32001: Request timed out'. A dispatch of dom-bloat right after returned {ok:true,code:'dispatched',queueDepth:1}. 500ms later status was {state:'busy',queueDepth:0} and the phase was ['dom-bloat','working']. The agent's next watch_for_issue(3s) returned watch-timeout and the phase stayed 'working'.
- suggested fix: Pass `extra.signal` from the tool handler into hubClient.waitForIssue/waitForSnapshot fetch calls, so the hub's res.on('close') removes the waiter. Cap timeout_seconds at 55 or send progress notifications. If the bridge cannot deliver a dequeued issue, re-queue it on the hub.
- verifier (confirmed): I reproduced this with a real MCP SDK 1.27.1 client against dist/index.js connect. watch_for_issue({timeout_seconds:30}) with a 3s client timeout threw 'MCP error -32001: Request timed out'. A dispatch right after returned dispatched/queueDepth 1. Status then went to busy with queueDepth 0, the phase became ['dom-bloat','working'], and the next watch_for_issue(2s) returned watch-timeout, so the issue was lost. Code matches: the mcpServer.ts tool handler ignores extra.signal, hubClient.waitForIssue sends fetch with no AbortSignal, and flushIssueWaiter hands the dispatch to the first registered waiter, which is the dead one. Any client timeout or user interrupt during a pending watch opens this window, which can last up to timeout_seconds (at most 300s).

## E2E-05 [minor] Agents that do not own a project can still acknowledge or resolve its issues
- file: packages/mcp/src/hubServer.ts:435
- detail: The internal acknowledge and resolve routes take no sessionId. resolveProject in mcpServer.ts lets any session target any active project it does not own. So an agent that was just rejected with lease-conflict can still change the owner's workflow. acknowledge moves an issue that was never sent to 'working' (widget shows 'With agent' and disables Send) and hides it from get_detected_issues. resolve moves it to 'verifying', and when the issue is still present this is recorded as a 'verification failure' in impact. This contradicts the one-owner-per-project model ('neither can read or consume the other's dispatches', packages/mcp/README.md).
- evidence: In mcp-loop.mjs, B's watch_for_issue got lease-conflict, then B's acknowledge_issue(dup) returned {acknowledged:true} and the phases became [['dom-bloat','detected'],['duplicate-requests','working']]. In mcp-honesty.mjs T3, while A owned the lease, B's resolve_issue(dup) returned {verifying:true} and the phase became ['duplicate-requests','verifying']. stats then reported '1 verification failure caught'.
- suggested fix: Send sessionId on the acknowledge/resolve internal routes. Reject the request (409, code 'lease-conflict' or 'not-owner') when another live session holds the project's lease, and consider requiring the caller to hold the lease itself.
- verifier (confirmed): Reproduced: session-less POSTs to /internal/.../acknowledge and /resolve succeeded while B held the lease. The phases became duplicate-requests 'working' and dom-bloat 'working' (via verifying, then verification-failed), and impact reported verificationFailures:1. The hubServer.ts:433-447 routes and resolveProject in mcpServer.ts do no ownership check. Downgraded to minor. The README's 'neither can read or consume the other's dispatches' is about separate projects, and dispatch consumption (dequeue) is session-checked. The browser verify route is also lease-free by design, so a non-owner resolve only starts an evidence-based check. The real harm is limited to a non-owner's acknowledge hiding an issue and inflating the verification-failure count.
