VibeCheck: In-Depth Analysis

What the product is, where it stands today, a GPS framing (Goals · Problems · Solutions), and a concrete path to make it a real success.

Repo: vibe-check monorepo npm packages @ 0.3.0 Site: vibecheck.wcgw.fun Written: 2026-07-25

Tip: open this file in a browser. Use print → “Save as PDF” if you want a PDF copy.

What it is

VibeCheck is a closed-loop “press check” for AI-built frontends. It watches a real browser session, names the defects vibe-coded UIs keep shipping, and can hand one concrete finding to the one coding agent watching that project — then verify the fix with fresh browser evidence rather than trusting the agent’s word.

Your agent shipped it. VibeCheck pulled the proof.
Live site: vibecheck.wcgw.fun

That is not generic APM. The wedge is agent-era quality: detect → dispatch → fix → prove.

What it does, product-deep

1. Runtime measurement (collectors)

FPS, long frames / LoAF attribution, memory, Web Vitals (LCP/INP/CLS), resources, console volume — continuous, not a one-shot Lighthouse run.

2. “Slop bestiary” (13 detectors)

Runtime and payload:

  • DOM bloat, duplicate requests, console spam, memory leak, layout thrashing
  • Unoptimized / large images, long-task attribution, resource bloat, heavy libraries

Discoverability:

  • SEO (~20 checks)
  • AEO (~9 checks: structured data, llms.txt, JS-only content, AI crawlers, MCP discovery)
  • Web essentials

This is a deliberate catalog of what AI-generated UIs tend to get wrong, not a generic perf suite.

3. Agent workflow (the real product)

v0.3.0 is not “metrics + clipboard.” It is:

  • Project-scoped hub (parallel dev servers don’t fight over port 4200)
  • Exclusive watcher lease (one agent owns one project)
  • Durable phases: detected → sent → working → verifying → fixed / regressed
  • Stable page-aware issue identity across refresh/restart
  • Browser-evidence verification (stale/worsening metrics cannot mint a receipt)
  • Local impact ledger (fixes, regressions, conservative before/after deltas)
  • setup / register / doctor for Codex, Claude Code, Cursor

10 MCP tools: list_projects, get_project_impact, get_performance_snapshot, get_detected_issues, get_fix_suggestions, watch_performance, watch_for_issue, acknowledge_issue, resolve_issue, release_project.

4. Growth surfaces beyond the npm package

  • Interactive landing (“break this page,” live gauges, live widget on the marketing site itself)
  • URL scan for SEO/AEO without install
  • Fix guides per problem slug (SEO content engine)
  • Claude skill under skills/vibe-check/
  • Recorded real MCP round-trip GIF (not a mock UI)

Current state

Engineering maturity: high for a solo OSS product

Strengths

  • Clear package boundaries; core stays zero-deps; protocol is the contract
  • Immutable / fail-closed multi-project design (leases, ambiguous project_id)
  • CI is serious: typecheck, unit tests, build, bundle size budget (45KB gz main chunk), packed Playwright MCP round-trip, publish dry-run
  • Release automation + production smoke for the public site
  • Dogfooding: marketing site must pass (or honestly surface) its own SEO/AEO detectors
  • ~79 test files; E2E covers dispatch, SEO suggestion fidelity, persistence, regression, multi-project isolation, client setup

Product maturity: 0.3 feels like a real v1 of the loop

Changelog honesty is a feature: v0.2 closed the “demo shows more than npm” gap; v0.3 made workflow durable and verifiable. That is rare discipline for early OSS.

What is not productized yet:

  • Hosted multi-user issue tracking (explicit non-goal in designs — good)
  • Automatic agent pickup without a human “Send to agent” / watch session
  • Continuous CI integration as first-class (Playwright exists for you, not for customers’ pipelines)
  • Non-React first-class UX
  • Monetization of any kind

GPS — Goals · Problems · Solutions

Goals (what “great success” should mean)

Near-term (next 3–6 months) success is not “become Datadog.” It is:

  1. Default conscience for AI-built React apps among Claude Code / Cursor / Codex power users
  2. Time-to-first “Send to agent” green receipt < 5 minutes for a greenfield Vite/Next app
  3. Social proof: stars, a launch moment, 2–3 known creators using it on camera
  4. Retention loop: people keep the hub running because impact ledger + regression reopen feel valuable week after week

Longer-term success:

  1. Category ownership of “browser evidence → coding agent” for frontend quality
  2. Optional hosted/pro layer (team impact, CI gates, shared projects) without selling out local-first DNA
  3. Framework surface area beyond React without diluting quality

Problems (user + product)

User problems (why this exists)

  • Agents ship UIs that look done and still thrash, leak, double-fetch, bloat the DOM, and fail SEO/AEO
  • DevTools / Lighthouse don’t speak MCP or own a fix workflow
  • Copy-paste “fix this” prompts are not delivery; agents lie about having fixed things

How to make it a great success

Principle: ship the habit, not more surface. You already have more product than most people will discover. Success = many people complete one real loop, then leave it on.

Phase 0 — Unblock discovery (1 week, non-negotiable)

  1. Set GitHub homepage to https://vibecheck.wcgw.fun, add topics: mcp, performance, web-vitals, claude-code, cursor, react, devtools
  2. Pin a 60-second demo (you already have the real GIF — lead with it)
  3. One sharp README opening: problem → 3-step setup → green receipt screenshot
  4. Fill the screenshot TODOs (Monitor + Agent tabs at minimum)
  5. Align AGENTS.md / skill text with 0.3 tools so agents install correctly

Without this, more features are invisible R&D.

Phase 1 — Collapse time-to-wow

North star metric: minutes from clone to first successful watch_for_issue delivery.

Move Why
npx vibe-check up one command Hub + open doctor UI + print watch paste in one process
Auto-watch instruction in setup that agents can run as a skill/slash command Remove “user must babysit lease” for first run
In-widget “Copy full setup pack” Single clipboard block for the user’s agent of choice
Zero-config projectId from package.json name + strong default beacon Fewer props to forget
Next.js / Vite official templates One-click StackBlitz/CodeSandbox with green path

If setup stays “three terminals and a green light,” you stay a power-user tool.

Phase 2 — Own a weekly ritual (retention)

Impact ledger is the seed of habit. Make it shareable and social:

  • Weekly impact card export (Markdown for README / PR description / standup)
  • “Regression caught” as a first-class celebration (agents over-claim; you catch them)
  • Optional CI gate later: fail PR if critical detectors fire in a Playwright smoke

People keep tools that make them look careful.

Phase 3 — Distribution that matches the craft

  1. Launch sequence: Show HN + r/ClaudeAI + r/cursor + X threads with the real GIF
  2. Agent marketplaces / skill registries (Claude skill, Cursor rules, Codex skills)
  3. Creator co-marketing: 3 influencers build a deliberately broken app live; VibeCheck catches it
  4. Comparison content: “Chrome DevTools MCP vs VibeCheck” — complementary: DevTools is the microscope; VibeCheck is the press check
  5. SEO/AEO of the site itself — double down: /fix/* guides + scan leaderboard as evergreen acquisition

Avoid: generic “perf monitoring” SEO wars with Lighthouse clones.

Phase 4 — Expand surface carefully

Expand When
Vue/Svelte thin adapters (or official headless recipes) After React TTFW is <5 min and launches land
Vanilla web component shell Same
Hosted hub / team impact (paid) Only after local habit is proven; keep local free forever
More detectors Prefer precision and fix quality over count; 13 named well > 40 noisy
Production RUM mode Tempting; risks category confusion — keep as explicit “prod beacon” later

Phase 5 — Business model (only after pull)

Local OSS free forever for individuals is the right default. Monetize teams:

  • Shared impact across machines
  • Org-wide detector policy
  • CI tokens / hosted verification runners
  • Priority detector packs (e.g. ecommerce image discipline)

Do not monetize the basic send-to-agent loop early; that is the growth engine.

Strategic risks to manage

  1. Chrome / platform MCPs absorb “browser metrics for agents” — Counter by staying the opinionated quality conscience (bestiary + verify + impact), not a thin metrics pipe.
  2. False positives kill trust — Memory leak and duplicate-request detectors must stay conservative; you already exclude self-traffic. Treat FP rate as a P0 product metric.
  3. Over-branding vs clarity — “Live press check” is excellent after people get it; cold traffic still needs plain: perf + SEO monitor that sends issues to your coding agent. Lead with plain; keep press check as signature.
  4. Scope creep in apps/web — Brand system is beautiful; distribution ROI may beat another proof-rail polish pass.
  5. Solo founder burn — Freeze non-essential design systems; open “good first issues” (adapters, screenshots, detector recipes) once stars exist.

Closing judgment

VibeCheck is not a half-built idea. It is a sharp, well-engineered product sitting at the intersection of:

  • exploding AI-generated frontend volume,
  • MCP as the agent I/O standard, and
  • a genuine hole between Lighthouse scores and “my agent actually fixed the jank.”

v0.3’s durable workflow + browser-verified impact is the right product spine.

Great success here looks less like “more features” and more like:

Thousands of React (then broader) apps leave VibeCheck mounted in dev; agents routinely lease projects; teams paste weekly impact; the name “press check” becomes the shorthand for agent-era frontend QA.

You already built the instrument. The lever now is make the first green receipt inevitable, then make the world hear it.
